### Two real defects the browser run exposed

1. **Topbar account menu lost its links.** The redesign had added `role="menu"` / `role="menuitem"`
   to the dropdown. On an `<a href>`, `role="menuitem"` *overrides* the implicit `link` role, so
   "My Profile" and "Change Password" stopped being links — and the ARIA menu pattern was only half
   implemented (no arrow-key roving focus), which is worse than none. Rebuilt as a labelled `<nav>`
   disclosure with `aria-haspopup="true"`; the items are ordinary Tab-reachable links again.
2. **Rider offline baseline was stale.** Inspected the diff before touching it: the change is the
   intentional Rider reordering — duty/online panel promoted above the fold, secondary duty chat
   demoted to the bottom (exactly what `47-rider-mobile-redesign` asserts). Baseline updated
   deliberately. Note this baseline also embeds seeded values, so it drifts when the seed changes.

### Shared views brought onto the design system

The audit previously marked several routes `REDESIGNED` that still rendered no shared dashboard
component. Rather than edit ~26 near-identical page shells, the three **shared views** they all
delegate to were upgraded, which fixes every role's route at once:

| Shared view | Routes covered | Change |
|---|---|---|
| `components/notifications/notifications-view.tsx` | 7 (`/*/notifications`) | Shared page header + 3 own-inbox summary cards + real empty state |
| `components/complaints/complaints-view.tsx` | 8 (`/*/complaints`) | Shared page header + 5 status cards that filter via URL + no-results state distinct from no-data |
| `components/management/report-view.tsx` | 11 (`/management/reports/*`) | Shared header + breadcrumb + `ResponsiveDataView` so rows become labelled cards below `md` |

Both new summaries are single grouped Prisma queries in `lib/services/page-summaries.ts`
(`getNotificationInboxSummary`, `getComplaintListSummary`) — one query per page, not one per card,
counting the **whole** result set rather than the fetched page. Notifications reuse the list route's
own `userId` scope; complaints reuse `complaintsWhereForUser()`, so neither can aggregate anything
the signed-in role may not already list.
